Diagram Maker 0.1.0-internal.6 사내 시험 안내
============================================

준비
----
OFFLINE_INSTALL_KO.txt에 따라 비동기화 로컬 폴더에 압축을 풀고 configure-llm.cmd로
승인된 사내 LLM을 설정한다. start.cmd 실행 후 health-check.cmd와 test-llm.cmd를 실행한다.
웹 주소: http://127.0.0.1:5080
이 ZIP은 .NET 런타임, Node.js, 프런트엔드와 C/C++ 분석 작업자를 포함한다.
실제 사내 모델의 의미 품질은 배포 PC에서 검증하지 않았으며 아래 절차로 확인해야 한다.

1. 고정 코드로 의미 생성 확인
---------------------------
코드 블럭 다이어그램에서 작업 제목을 입력하고 언어를 C#으로 선택한다.
Thinking은 OFF로 두고 아래 코드를 한 블럭에 붙여넣는다.

enum JobState { Idle, Running, Done }
class Job {
    JobState state = JobState.Idle;
    public bool Run(int count) {
        if (count <= 0) return false;
        state = JobState.Running;
        for (int i = 0; i < count; i++) Store.Save(i);
        state = JobState.Done;
        return true;
    }
}
class Store {
    public static void Save(int value) { }
}

Flow, Sequence, Class, State, 코드 관계도 출력을 추가하고 생성한다.
- count <= 0의 조기 반환 뒤에는 저장 호출이 없어야 한다.
- 정상 경로는 반복문 안에서 Save(i)를 호출하고 이후 Done 상태와 true 반환으로 끝난다.
- Job과 Store 사이의 호출, 각 단계의 원본 근거, 분기와 반복 범위를 확인한다.
- 의미 생성 성공 여부와 정적 구조를 구별한다. 미완료 표시는 진단과 함께 기록한다.
- SVG/PNG 다운로드를 열어 배경·노드·선·문자와 편집 결과를 확인한다.

C/C++ 시험은 새 작업에서 언어를 C/C++로 선택하고 다음 코드를 붙여넣는다.

int save(int value) { return value; }
int run(int count) {
    if (count <= 0) return -1;
    int total = 0;
    for (int i = 0; i < count; ++i) total += save(i);
    return total;
}

Flow와 Sequence에서 조기 반환, 실제 save 호출의 반복, 최종 반환 근거를 확인한다.
같은 고정 사례를 각각 새 작업으로 3회 생성하여 결과의 핵심 동작과 실패 유무를 비교한다.

2. 큰 입력·전체 완료·이어하기 확인
--------------------------------
- 입력 한도는 블럭당 100,000자, 전체 1,000,000자, 최대 20블럭이다.
  한도를 넘겨 붙여넣어도 텍스트는 잘리지 않는다. 초과 안내가 있으면 크기를 조정한 뒤 저장한다.
- 약 1,200줄/40개 이상 함수/여러 클래스의 고정 C++와 실제 문제 코드를 각각 새 작업으로 3회 시험한다.
  Thinking OFF, Flow 및 여러 형식을 선택하여 전체 상세 완성 후 그림이 열리는지 확인한다.
  목표는 전체 300초 이내이며 5분 초과 시 안내와 함께 기본 900초까지 계속 생성하는지 확인한다.
- 진행 중 취소하거나 기본 900초 예산 종료 후 이어하기를 누른다.
  두 차례 이상 이어하기를 수행하고 전체/이번 실행의 완료·재사용·요청·실제 전송 수와 대기 시간을 확인한다.
  중단 후 '부분 결과 열기', 남은 결과, 이전 생성 이력과 원본 근거를 확인한다.
- 입력이나 모델·토큰 설정을 바꾸면 체크포인트가 재사용되지 않을 수 있다.
- 서버를 재시작한 뒤 저장한 작업을 열어 완료 결과와 이어하기 상태가 유지되는지 확인한다.
- 문맥에 들어가지 않는 단위와 잘린 응답은 미완료로 표시될 수 있다. 임의로 의미 성공 처리하지 않는다.

3. Git 분석 확인
---------------
승인된 비동기화 로컬 저장소를 등록한다. 작은 변경과 큰 변경을 각각 선택하여 생성한다.
변경 전후 근거, 분기·호출 관계, 전체 완료 후 공개, 취소·이어하기와 완료 결과 재사용을 확인한다.
대용량 Git 저장소는 PATH에 사내 승인 Git이 설치되어 있어야 한다.

4. 설정과 결과 기록
-------------------
기본 입력/전체 문맥 상한: 각각 200,000토큰. 출력 상한: 60,000토큰.
완성된 JSON 예제: config/llm-policy.example.json. 적용/단위 안내: config/LLM_POLICY_KO.txt.
MaxInputCharacters는 문자 수이며 기본 2,000,000이다. 60,000자와 200,000토큰은 다른 제한이다.
새 의미 묶음은 기본 입력 48,000/생성 출력 8,000/검토 출력 2,000토큰이며 서버 상한을 존중한다.
실제 서버의 전체 문맥 한도가 다르면 Llm.MaxContextTokens를 승인된 값으로 설정한다.
입력과 출력 예약은 합산한다. 서버 토큰 계산 미지원 시 진단에는 추정치로 표시된다.

사내 화면의 '요청 오류 진단' 또는 각 작업의 '작업 진단 다운로드'에서 다음 항목을 확인한다.
최초 응답 검증 실패와 후속 문자/토큰 초과 기록을 함께 확인한다. 파일 반출 없이 화면에서 확인할 수 있다.
- 패키지 버전, 시험 날짜, 사례 이름, 반복 번호
- 의미 생성 성공/미완료, 분기·반복·호출·근거 확인 결과
- 전체 완료 시간, 누적/이번 실행 시간, 완료/재사용 단위 수, 실제 전송 수
- 오류 코드, 실패 단계, 토큰 사용/추정 여부, 출력 방식
- 최근 요청의 실제 출력 한도·사용 토큰·종료 사유, 상위/하위 묶음과 시도 번호
- 미해결/복구 완료 구분, 조건 반전·동작 누락 등 항목별 검토 사유

초기 생성 최대 12항목과 항목별 검토를 적용한다. 기본 검토 출력은 2,000토큰이다.
검토 잘림/형식 오류는 검토만 복구하며, 생성 수정은 항목당 1회다. 검토 요청 수가 늘 수 있으므로
완료 여부·의미 품질·총 요청 수와 시간을 함께 비교한다. 원본 의미 오류를 통과 처리하지 않는다.
동일 문제 코드로 Thinking OFF 신규 생성 3회를 실행한다. 업그레이드 전의 진행 중 실행은
바뀐 프로토콜 요청을 다시 수행할 수 있으며 저장된 결과와 원본 근거는 계속 조회할 수 있다.

진단 JSON에는 코드·프롬프트·모델 응답·실제 서버 주소·체크포인트 값이 포함되지 않는다.
실제 정책 파일, 저장 데이터 파일, 사내 코드가 보이는 화면은 진단 자료에 첨부하지 않는다.
진단 JSON과 위 결과를 기준으로 실패를 재현하고 개선한다.

5. 코드 생성 자동 검사와 텍스트 보고서
--------------------------------------
start.cmd로 서버를 실행한 다음 LLM 점검 탭에서 '코드 생성 검사'를 누른다.
고정 C#과 C++ 코드의 실제 파서·공유 의미 생성·독립 검토·페이지 구성을 Thinking OFF로 실행한다.
별도 입력이나 저장소 등록은 필요하지 않다. 검사 결과는 새 사용자 작업으로 저장되지 않는다.
'검사 보고서 다운로드'를 눌러 적용된 비민감 설정과 요청별 오류 진단을 텍스트로 저장한다.
일반 연결/DiagramIR 검사 성공과 코드 생성 검사 성공은 각각 확인해야 한다.

명령으로 검사하려면 test-code-diagram.cmd를 실행한다. 보고서는 배포 폴더의 diagnostics 아래
code-diagram-*.txt로 저장된다. 실패해도 응답 보고서는 남으며 종료 코드는 0이 아니다.
코드 블럭/Git 작업 화면에도 '텍스트 진단 다운로드'가 있다. 실제 작업의 실패 단계와 HTTP 상태,
고정 오류 분류, 출력 방식, 입력·출력 한도, 필드 길이, 상위 묶음·시도를 함께 확인한다.
HTTP 400의 원인이 미확인이라면 같은 시각의 사내 서버 로그를 관리자가 확인한다.
앱은 서버 오류 응답 원문을 저장하거나 보고서에 넣지 않는다.

고정 합성 검사 통과는 실제 문제 코드의 의미 품질과 300초 목표 달성을 뜻하지 않는다.

6. accuracy.1 실행 정확도 확인
-----------------------------
Sequence에서 함수의 전체 호출, 첫 실패에 따른 반환, 정상 반환을 한 그림에서 확인한다.
같은 이름의 호출도 서로 다른 위치에서 발생하면 각각 남아 있어야 한다. '호출·조건·반환과
원본 근거'를 펼쳐 정확한 원식과 반환값을 확인하고 각 근거 버튼으로 원본 위치를 연다.
외부 함수의 구현·Sleep 단위·미확인 반환값을 이름만으로 확정하지 않는지 확인한다.
Git에도 State를 선택할 수 있다. 같은 변수·출발·도착 전이의 조건만 변경하면 수정으로
표시되고 변경 전후 근거가 모두 열려야 한다. enum만 있거나 외부 호출로 상태가 불확실하면
전이를 만들어서는 안 된다.

함수 전체 의미 계획과 검토는 형식 간 공유한다. 분할이 없는 함수당 2회가 추가되므로
40함수는 80회, Git 양쪽 리비전은 160회가 추가된다. 실제 요청 수와 완료 시간을 비교한다.
긴 함수는 완결된 형제 영역 사이에서 분할한다. 단일 제어 영역 또는 전체 검토가 예산을
넘으면 원문을 자르지 않고 미완료로 남긴다. 기존 900초와 수정 1회 한도는 유지한다.
구버전 코드 블럭의 이어하기는 고정 입력에서 새 분석으로 시작한다. 과거 그림·근거·편집은
그대로 열리는지 확인한다. 사내 실제 LLM 품질과 PostgreSQL 연결 검증은 별도 수행한다.
